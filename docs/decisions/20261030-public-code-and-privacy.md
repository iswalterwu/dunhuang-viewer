# D-019 代码仓库保持公开，发布内容必须先完成隐私脱敏

- 日期：2026-10-30
- 状态：accepted（用户已批准公开脱敏规格Gate1，含最小必要源码/配置/脚本；另已明确授权清理历史与提交者信息，并受保护更新origin的main和功能分支）
- 取代：D-009中「仓库必须为私有」的可见性要求；不改变其代码权威、部署通道和合并后才可部署的约定

## 背景

用户已确认软件评审与既有待验风险，允许进入交接、PR与合并流程。随后用户明确要求代码仓库保持公开，同时隐去个人资料获取渠道、私人网关与存储部署信息、账户信息等，并在全面检查和修改后再继续交付。

## 备选方案

1. 将整个代码仓库改为私有。
2. 保持公开，但只编辑少数说明页面，保留其他文本、运行默认值和旧历史中的个人信息。
3. 保持公开，按明确的发布边界审计文档、归档、源码和配置；私人原件在仓库外保存，公开内容经脱敏验证后才交付。

## 结论

- 采用方案3。公开的是代码、通用部署说明、学术与许可信息和可公开的验证摘要，不是私人运行环境或资源库。
- 个人账户、私人邮箱、真实服务入口/网络地址/网关拓扑、工作站与宿主存储路径、设备实例信息、个人资料接收渠道、原始操作记录等不应作为公开示例或默认值发布。
- 收藏机构、馆藏号、公开学术参考、影像谱系、许可限制与来源不明的事实必须保留。隐私处理不能伪造成机构直接授权或获取许可；详细接收记录可保留在非公开档案中。
- 原始审核和测试记录不冒充公开脱敏原文：私人原件保留在仓库外，公开衍生版本须标明脱敏属性，不更改通过/失败/跳过数、限制条件或独立结论。
- 仅修改当前树不能消除旧提交。Git历史、提交者身份和其他公开引用需单独盘点；重写已发布历史、强制推送、删分支/标签、更名或转移仓库均须另外取得明确授权。
- 不为脱敏部署或访问私人存储环境，不改变文件写入、内存限额、登录保护、目录身份/许可算法或现存运行数据。涉及运行配置或输出标签的必要修改须在专门规格中声明、独立实施与复验。

## 取舍理由

- 满足用户保持公开代码的决定，同时避免通用软件说明变成私人基础设施说明。
- 只检查Markdown会漏掉归档、JSON、脚本、注释和运行默认值；只做字符串替换可能破坏链接、验证证据、许可或可运行性。
- 不隐瞒既有Git历史暴露，也不把普通提交/删除当前文件宣称为历史清理。已被第三方取得的副本不能保证撤回。

## 影响

- `AGENTS.md`及总方案须引用本决策；旧D-009的部署约定继续有效，可见性以本决策为准。
- `specs/public-release-privacy/spec.md`登记发布脱敏范围、验收和未授权操作；Gate1批准前不进入Plan/Implement。
- `catalog-foundation`既有软件评审和Gate2批准不被抹除，但PR/合并仍须等待本次脱敏工作与相关发布决策完成。正式部署与真实材料验收仍需单独授权。
