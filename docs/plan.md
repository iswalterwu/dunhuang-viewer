## 1. 背景与目标

### 1.1 定位与愿景

本项目从「NAS 高清查看器」（v0，仓库名 `dunhuang-viewer`）升级为**面向所有敦煌研究者的开放资源整理平台**（D-010）：

- **长期**：把全球可开放获取的敦煌资源与内容细致梳理、统一编目、互相关联——写卷、壁画、研究论文、参考资料、评论，以及写卷之间、壁画之间、壁画与写卷之间的联系
- **第一步**：整理现有材料——目前只有敦煌写卷（书法相关；其中少量经核查并非敦煌出土，§1.3），先做细致的标注、分类与命名规范
- **随后**：寻找相关资源，补充并建立链接
- **工程**：前后端分离（D-011）；v0 查看器在迁移期间继续在线服务

### 1.5 Phase 1 目标与非目标

**目标**（整理现有材料）：

1. 为现有 6,096 个影像目录建立统一目录：每件写卷一条记录（同一编号的多个影像目录合并，如法藏 849 个目录对应 740 个编号），内部 ID 稳定、不依赖磁盘路径
2. 记录每件写卷的全部编号（主编号 + 旧编号 / 别号），并注明出处
3. 从现有目录名中解析出编号、题名、时代、材质、尺寸等字段，标出异常，生成规范名称
4. 按统一体系标注文献属性与书法属性（§4.2、§4.3），每条标注可追溯来源
5. 按馆藏、文本、文献类型、时代、书体分类浏览，取代按来源批次的目录分类
6. 为每件写卷记录出处认定、影像谱系、来源与许可

**非目标**（Phase 1 不做）：采集外部资源、壁画与论文库、面向公众开放注册、改动原图内容、修改磁盘目录与文件名（D-013）。

## 2. 用户与核心循环

- **用户**：敦煌研究者——文献学、书法、佛教史、历史、艺术史方向的研究者与学生；Phase 1 期间仍是所有者及授权用户（登录墙；账户实例与数量非公开），开放方式在 Phase 3 另定（D-012）
- **访问通道**：局域网 / Tailscale 入口由部署方显式配置；如开放 v0 公网访问，须配置 HTTPS、可信代理头及登录墙。私人入口与网关拓扑不公开（architecture.md §1）；目录服务 Phase 1 不接入公网
- **核心循环**：影像 + 目录信息 → 统一编目（稳定 ID + 多编号对照）→ 标注（文献属性、书法属性，带来源）→ 关联（同文本、缀合、同书手、正背面、壁画与写卷）→ 检索与浏览 → 研究成果回填
- **与现有平台的关系**：链接而非复制。外部资源以 IIIF 清单、原始页面链接、编号对照的方式接入；本地高清影像只在许可允许的范围内展示（PD-11）

### 4.2 文本定名与文献分类

- **定名本身是研究成果**：同一残卷在不同目录里可能有不同定名，需记录「谁定的名、出自哪部目录」
- **佛典**：以《大正藏》编号作为文本锚点（CBETA 采用同一编号，如 T0262《妙法莲华经》），再记卷次、品名
- **非佛典**：按文献类型分类——儒家典籍、道经、文学、类书、社会经济文书（契约、诉状、差科簿、社司转帖等）、其他；Phase 1 先用粗分类，细则在标注体系 feature 中定
- **载体类型**（先于文献类型）：写本、刻本（含大藏经零本）、捺印、拓本、绘画（白描、经变图、绢画等）
- **出处认定**：是否敦煌出土单独认定（已确认 / 待核 / 非敦煌），不从目录名继承（§1.3）
- **原始著录保留**：现有目录名、IIIF 清单字段原样保存，作为每条记录的「原始名称」

### 4.5 命名规范原则（已确认，细则见 D-013）

1. 原始名称永久保留，规范名称由结构化字段生成，不手写

## 5. 原则与红线（2026-10-27 确认；AGENTS.md §4 引用本节）

1. **许可合规**：每件资源记录来源机构、获取渠道、许可条款与署名文本；IDP 内容默认仅限个人或非商业复用 [6]，Gallica 允许免费非商业复用但须保留出处 [6]；许可不明的资源不对外展示高清影像
2. **可追溯**：每个字段、每条标注都记录来源（人工 / AI 预标 / 外部目录 / 文件名解析）、作者、时间、置信度，可查历史、可回滚
3. **学术区分**：区分「转录自某目录」与「本项目判断」；定名、断代、书体、缀合等判断都要注明依据
4. **非破坏**：整理不丢失原始名称与原始文件；改动原图目录一律先备份、写计划、留日志（PD-02）
5. **身份稳定**：内部 ID 与磁盘路径解耦；外部编号是属性，不是主键
6. **开放标准**：影像与清单向 IIIF 靠拢，标注采用 W3C Web Annotation 模型（D-017）
7. **先整理、后扩展**：Phase 1 只围绕现有材料；外部资源在 Phase 2 接入
8. **NAS 安全**：继续遵守 D-005 内存红线；批量任务放低峰

## 6. 架构方向（前后端分离，D-011）

- **现状（v0）**：FastAPI 单体，同时提供页面、图块与接口（architecture.md）
- **目标**：
  - 后端：目录与标注 API（REST + OpenAPI）、影像服务（v0 的 DZI 图块逐步向 IIIF Image / Presentation API 靠拢）、数据库、后台任务（导入、解析、图块生成）
  - 前端：独立的单页应用（浏览 + 标注工作台），只通过 API 访问；查看器沿用 OpenSeadragon，或换用 IIIF 原生的 Mirador
- **迁移方式（渐进，D-016）**：Phase 1 的新功能（目录、标注、浏览）直接以「API + 新前端」实现；v0 查看器继续在线，等新前端覆盖其功能后再替换
- **选型（D-016）**：数据库 PostgreSQL；前端 Vue 3 + Vite + TypeScript（沿用已有技术经验）；IIIF 影像服务方案在首个涉及影像服务的 feature 中另登 ADR；新服务上线前评估 NAS 内存（RK-01）

## 11. 文档体系与目录结构

原则：**单一作者、机读优先、决策留痕**。文档地图见 AGENTS.md §1。

文档纪律：

- 每份规范只有一个权威作者位置；README 只导航不复制数值（防双份漂移）
- 所有"为什么"写进 ADR 或规范条目，不散落在会话里
- 方案变更先改 docs 再改代码；实现与 docs 冲突以 docs 为准
- 功能开发一律走 spec-driven 工作流（AGENTS.md §2）
- 运行参数的权威是 `docker-compose.yml`（环境变量）与代码默认值；文档引用参数名，不另抄数值
- 本文的盘点数字都标明日期，只作为当日快照；外部事实注明出处（§4 参考）

v0 代码目录（单体）：`app.py`（服务）、`pyramid_worker.py`（后台生成器）、`stitch_apply.py` 与 `auto_huge*.sh`（宿主机脚本）、`static/`（页面）、`Dockerfile`、`docker-compose.yml`、`requirements.txt`；
运行时产物（不入库）：`.env`、`build.log`、`cache/`（图块、缩略图、拼接方案、用户表、生成状态与日志；根目录另有 2026-10-21 数据整理的脚本与记录，§1.4）。
前后端分离后的目录结构在 PD-17 确认后规划。
